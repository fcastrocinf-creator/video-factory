3. Fixing the cascade behavior
The bug pattern in your current code is conflating two separate concerns: intra-provider retry (transient 5xx, network blips, rate-limit with Retry-After ) and inter-provider failover (provider down, quota exhausted for entire window, content-policy reject). They need different policies.

The decisive rules:
1. isContentRejection → skip to next provider IMMEDIATELY, never retry within. A 400 from gpt-image-1 saying "policy violation" will keep saying that.
2. isDailyQuotaExhausted or online_prediction_requests_per_base_model 429 → open the circuit for that provider for 60s AND skip to next. Don't burn budget probing.
3. Transient (5xx, network reset, generic 429 without per-base-model metric) → exponential backoff with jitter, up to 3 attempts.
4. Auth (401/403) → fail loudly, do not retry, do not cascade silently — this should page an operator (it's a config bug, not a runtime fault).
Error classifier responsibility: put it INSIDE each ImageProvider's generate() so the cascade doesn't need to know provider-specific error shapes. Each provider maps to one of: { kind:
'transient'|'quota'|'content'|'auth'|'unknown', retryable, isDailyQuotaExhausted,
isContentRejection } . This is your existing interface — the bug is that nobody is reading the kind field at the cascade layer.
4. Throttling / rate-limit design
Recommendation: Bottleneck per-provider limiters keyed by provider ID, configured per provider's documented RPM/IPM, paired with Cockatiel circuit breakers.
Why Bottleneck over p-queue/p-limit: it supports a reservoir that refills on a schedule (matches Google's IPM token-bucket exactly), supports maxConcurrent and minTime simultaneously, has clustered Redis support if you later horizontally scale workers, and exposes depleted / error events for observability. p-queue is simpler but lacks reservoir semantics; plimit is concurrency-only. npm + 3
Concrete per-provider settings (starting points, tune from logs):
Gemini API (Nano Banana, Tier 1): reservoir 10/60 s, maxConcurrent 4, minTime 6000 ms. Vertex Imagen (assuming a 5–20 RPM default for the auto-created project per community forum reports; treat 5 RPM as worst case): reservoir 5/60 s, maxConcurrent 2. BFL direct: maxConcurrent 6, minTime 200 ms (BFL is async polling, so concurrency cap matters more than RPM). fal.ai: maxConcurrent 8, minTime 150 ms.

Recraft: maxConcurrent 4, minTime 500 ms. OpenAI gpt-image-1: maxConcurrent 3, minTime 1000 ms.
Burst control at the orchestration layer: even with per-provider throttling, do NOT fire all 22 scenes' generate() in Promise.all . Use p-queue or a Bottleneck at the rip level with maxConcurrent 6-8 across all providers combined, so cascades from a failed provider don't dogpile the secondary. The 22-parallel pattern is the proximate cause of your current spike failures.

6. Safety / content policy strategy

Empirical permissiveness ranking for legitimate-but-sensitive cases (medical, children's products, anatomy in product context), worst to best for production:
1. gpt-image-1 (OpenAI) — most aggressive. Microsoft Q&A threads document false-positive blocks on "child + puppy on beach" scenes. It scans both prompt AND output and silently fails the entire call. Never put it ahead of others on health/pediatric presets.
2. Imagen 4 / Nano Banana (Google) — strict on anatomical terms (will block isolated "skin," "body parts"), but generally pass educational/medical-illustration framings. Default-safe for D2C consumer products including baby goods, as long as prompts use parental/branded language ("baby teether held by parent," not "child's mouth"). Glbgpt
3. Flux 2 Pro (BFL) — most permissive of the major commercial APIs for legitimate content. safety_tolerance: 2 is the production-balanced setting. Strong on real-people-ish scenes that gpt-image-1 will reject.
4. fal.ai-hosted open models (Flux Dev, SDXL, Wan) — most permissive overall; appropriate as a fallback only because they're also the lowest brand-control. Use them sparingly for the "all primaries failed, render anything legitimate" emergency lane.
Prompt-engineering pattern (no jailbreaks, just disambiguation):
Replace clinical anatomy terms with brand/role language: "doctor expert" → "smiling healthcare professional in white coat reviewing product label"; "pediatric" → "for parents and small children, family-friendly setting." Always include explicit non-violation phrases when context is borderline: "wholesome family photography, soft daylight, professional advertising style." Use structured prompts (subject + action + context + style) — BFL's prompting guide explicitly recommends this and disallows negative prompts; never write "no violence" because the filter sees the word. Glbgpt Pre-flight prompts through a quick policy classifier (one Gemini Flash call, ~$0.0001) on flagged presets (medical, children, health) and rewrite if the classifier scores >0.7 risk.

8. Graceful degradation when ALL providers fail
In order of preference:
1. Try a relaxed-prompt regeneration via your cheapest available provider (rewrite prompt to remove anything that looks like a policy trigger).
2. Use a brand-safe placeholder — render the scene in Remotion with brand-color background + product overlay + the scene's text/subtitle. Acceptable for a B-roll scene and the rip still completes.
3. Skip the scene entirely if it's a B-roll filler (metadata flag optional: true ); compositor extends the preceding scene's duration to cover the audio.
4. Pause the rip and emit an actionable diagnostic (see §9) only if a hook scene (scene 0 or 1) fails fully — those are visually critical.
The rule: the rip MUST complete unless a non-skippable hook scene cannot be rendered. Manual retries are forbidden by your "100% automatic" requirement.
9. Observability / diagnostics
Minimum useful telemetry per rip:
Per scene: { scene_id, provider_used, attempts: [{ provider, status, latency_ms, error_kind?, error_message? }], elapsed_ms, fallback_depth } . Per provider per rip: cumulative success, fail-by-kind (quota/content/transient/auth), p50/p95 latency, circuit-open events. Per rip: total cost (computed from provider × image-count × pricing table), wall-clock duration, degraded-scene count. Store as columns on the rip row in your libsql/Drizzle DB; expose a /api/rip/:id/diagnostics route returning the JSON. The compositor stage embeds provider_used as a small overlay in dev mode for quick QA. Set up a single Slack/email webhook that fires only when (a) a rip completes with >3 degraded scenes, or (b) a provider's circuit stayed open >5 minutes — both are operatoractionable.
